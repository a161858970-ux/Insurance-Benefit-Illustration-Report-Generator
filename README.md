# 保险利益演示报告生成器（方向二）

课程《保险运营程序设计与实践》方向二作业：**通用渲染 + 个性化报告 + 多模态 H5**。
两层严格分离——渲染层（纯代码：解析/勾稽/图表/模块块/断言）数字不经 LLM；表达层（LLM：叙述、模块重排、合规改写）只做表达。

## 这是什么

一个**保险利益演示报告生成器**。输入课程给定的产品利益演示数据（7 款分红型养老年金/年金/增额终身寿，每款多组投保场景），输出可直接交付的客户利益说明：

- **12 份文字报告** —— 覆盖全部 7 款产品的通用渲染（各 1 份）+ 对拍场景 2 份 + 3 个客户画像的个性化对比组；
- **1 套 H5 交互页** —— 同一份数据可切换客户画像（模块顺序与叙述随之重排）与保单年度（图表竖线、表格行、关键值卡三重联动高亮）。

它回答的是"同一份演示数据，怎么既算得准、又说得对、还能对不同客户讲不同重点"三件事：

| 要求 | 做法 |
|---|---|
| **算得准** | 全部数字来自源 JSON，由代码解析、勾稽校验、格式化；**LLM 不参与任何数字的产生、计算与格式化** |
| **说得对** | 保证与演示两档严格分列、每个展示数字可回溯到 `字段@key` 出处、免责声明与数据来源/获取时点齐备、禁用词由代码扫描 |
| **讲给不同的人听** | 同一份数据按客户画像生成不同叙述顺序与语言风格的版本；模块顺序由 LLM 结构化输出、经白名单校验 |

产品形态（年金 vs 增额寿）、字段有无全部由数据驱动推断，换一款产品零改码。整体架构与硬性约定见 `SPEC.md`，交付与验证结论见 `VERIFICATION.md`。

### 工作链路

**数字全程走代码管道，LLM 只在中间被叫来"把数字说成人话"，说完还要被代码逐个数字查一遍。**

```text
利益演示数据/*.json   7 产品 × 12 场景，只读，不入库
   │
   │ ① loader       字符串转数值；"-" 判为不适用（不是 0）
   ▼
   │ ② reconcile    勾稽三恒等式（84 文件全量跑）
   │                  A 生存总利益 = 现金价值 + 累计领取
   │                  B 演示档生存总利益 = 保证档 + 累积红利
   │                  C 收益倍数 = 生存总利益 ÷ 累交保费
   │                  ✗ 任一不过 → 停机（说明数字被动过）
   ▼
   │ ③ summary      挑关键值做成摘要，每个值挂两个标签：
   │                  出处   （源：现金价值@59）
   │                  档位   （保证） / （演示、不保证）
   │                  代码同时算好：合计值、区间标签、档位词
   ▼
   ├─────────────────────────────┐
   │ summary_for_llm.txt         └──► 支线 B（H5，见下）
   ▼
   │ ④ 填模板        prompts/narrative_v6.md 的两个占位符
   │                  {profile_text} ← 按场景动态拼客户画像
   │                  {summary_text} ← ③ 的摘要
   ▼
   prompt_filled.txt             = 实际发给模型的完整提示词
   │
   │ ⑤ 调 API ★                 config.yaml 的 key → mimo-v2.6-flash
   ▼
   LLM 返回 ≤300 字纯文本（只做表达，不做任何计算）
   │
   │ ⑥ 数字回引                  文案里每个数字回摘要找出处
   │                              ✗ 找不到 → 退回重写 ≤2 次 → 仍败则降级占位符
   ▼
   │ ⑦ 合规扫描 ★               禁用词 11 词 / 保证·演示串档 / 合计缺区间
   │                              给付流覆盖不全 / 内部源标注泄漏
   │                              ✗ 命中 → 违规清单塞回提示词，改写 ≤3 轮
   ▼
   │ ⑧ 代码拼装                  剥掉 LLM 自己写的免责句 → 统一附加 1 次
   │                              + 数据来源 / 获取时点 页脚（代码拼，非 LLM）
   ▼
   │ ⑨ 终稿复核                  再回引一次，防改写轮引入新数字
   ▼
narrative_final.txt  × 12 份     output/m1、m2/*（7 产品）、m3/cmp_p_*（3 画像）
```

`★` = 经 API 调用模型（⑤ 必经；⑦ 仅违规时触发）。LLM 全项目共 **4 个调用点**：写叙述、排模块顺序、每模块写一句画像化解读、合规改写——其余一律是代码。

**支线 B：H5 交互页**（与主线共用 ②③ 的校验结果与同一批材料）

```text
②③ 的同一批材料 ──┬─ report.py    拼 7 个模块块，每行带 data-source="字段@key"
                   ├─ m3 manifest  画像 order / lead / 每模块一句（★ LLM 产出）
                   ├─ 逐年序列      5 条折线 × 75 点（点级 source）
                   └─ 关键值卡      34 张（数字级 source）
                            │
                            ▼
                  h5_build.py   可见文本 lint（复用主线同一套实现，页脚 require_footer=True）
                            │
                            ▼
                      data.json（53 KB）   ← 代码生成，非 LLM
                            │  fetch()
                            ▼
                index.html（10 KB 固定模板，0 个业务数字）
                            │
            ┌───────────────┴───────────────┐
            ▼                               ▼
  切客户画像 → 按 order 重排模块     拖保单年度 → 图竖线 / 表格行 / 关键值卡
                                     三重联动高亮（每个数字仍带 data-source）
```

两条线共用**同一套 lint 实现**，各自跑一遍：

- **主线** `validation/final_verify.py` —— 逐份报告判定：数字回引 / 禁用词 / 档位·区间·给付流覆盖·源标注（`output_tier_lint` 汇总）/ 免责 1 次且正文残留 0 / 页脚两行 / 无 Markdown 残留
- **支线** `validation/h5_lint_test.py` —— 六项：结构 / 数字回溯（序列 375 点 + 关键值 34 卡）/ 源码硬编码金额 / 可见文本 lint（复用主线同一套）/ `data-source` 机制 / 交互机制（切画像重排 + 切年度高亮）

## 怎么运行

```bash
# 环境：Windows / Python 3.11 / 无第三方依赖（纯标准库）
# 配置：复制 config.example.yaml → config.yaml 并填入 XIAOMI_API_KEY（config.yaml 不入库）

python src/m1_run.py ["<场景文件名>" [输出目录]]   # 单场景报告管道
python src/m2_run.py                               # M2 全链：84 勾稽+形态+合成自测+7 报告+终验
python src/m3_compare.py [画像id,画像id]           # M3 对比组（默认 3 客户画像；p_default 不进对比组）
python src/m4_run.py                               # 9 份正式产物模块化重生成
python src/h5_build.py ["<产品名>" "<场景文件名>"]  # 生成 H5 data.json（含六道 lint；换产品零改码）
python validation/final_verify.py                  # 12 份报告全量终验（扫 output/**/manifest.json）
```

## 硬性约定（违反即验收打回）

1. **数字不经 LLM**：LLM 输入=代码生成的摘要，输出必须过数字回引（三元组出处：字段@key@档位）
2. 换产品零改码（字段存在性驱动，禁止产品名分支）
3. LLM 输出过断言：禁词 / 档位 / 区间绑定 / 给付流覆盖 / 源标注 / 保障责任 + 页脚存在性
4. `config.yaml`（含 API key）永不入库；材料目录只读；提示词改动留档

## 踩坑速查（现象→原因，详见 DECISIONS）

- LLM 重试轮引入禁词 → 约束块必须每次生成（含改写）都重复（D014）
- 提示词版本替换静默未命中 → 锚没对上 `os.path.join` 分参数，替换后必须 assert（D034）
- `bool('false')=True` → config 解析要转真布尔（D050）
- 消歧邻域跨行污染 → 全部语境规则限定 token 行内 + 源声明 field+key 精确（D049）
- flash 长约束 JSON reasoning 爆 → `enable_thinking` 分层：首版关、改写开（D050）
- 页脚"数据来源："被当内部源标注泄漏 → source_lint 先剥页脚行再查（D053）
- LLM 句子带违规绕过终验 → 从不渲染的模块句是 lint 死角，须句级三查入库（D058）
- m3 对比组混入 p_default、"3/3"打印恒真 → 画像标 `compare:false` + 数量入判定（D057）
- execute_code 持久 kernel 缓存旧模块 → 验证一律走 fresh 子进程
